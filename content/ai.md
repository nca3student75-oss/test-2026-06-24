# 🤖 AI 활용 제작 과정

## 활용 원칙

AI가 완성된 게임을 한 번에 제작하는 방식보다, **플레이 테스트 → 문제 확인 → 수정 방향 결정 → AI 활용 → 다시 플레이**의 반복 과정에 사용했습니다.

이 프로젝트에서 중요한 것은 AI가 무엇을 만들었는가보다, **AI가 제시한 결과를 실제 환경에서 어떻게 검증하고 다시 수정했는가**였습니다. 화면에서 괜찮아 보이는 규칙과 UI도 실제 인쇄물, 실제 모바일 기기, 실제 플레이 상황에서는 전혀 다른 문제가 드러났고, 그때마다 사람의 판단으로 수정 여부를 결정했습니다.

## GPT

- 게임 기획과 규칙 논의 정리
- 플레이 테스트에서 발견한 문제의 구조화
- 룰북·게임 소개·제작일지 등 문서 작성 보조
- 보드게임 표지용·발표용 이미지의 초기 디자인 방향 수립
- 여러 버전 사이의 변경사항 비교와 제작 기록 정리

## Codex

- 웹게임 기능 구현 및 코드 수정 보조
- 기능 추가 전 파일 구조와 충돌 가능성 검토
- 이미지가 필요한 사건·장면 구성 제안
- 기존 웹게임 규칙과 새 기능의 연결 구조 검토

## Grok

Codex에서 제안된 이미지 구성을 바탕으로 이미지 수정·보강에 주로 활용했습니다.

- 1인 플레이 전용 컷씬 제작
- 기존 캐릭터 표정 3종을 5종으로 세분화
- 기존 6인 이미지 구성에 인간 플레이어 캐릭터 추가
- 추가 캐릭터의 5가지 표정 제작
- 기존 장면을 게임 상황과 맞게 수정·확장

## Adobe Firefly와 이미지 후처리

초기 표지 이미지는 생성형 AI를 통해 방향을 잡았지만, 실제 발표·인쇄물에 사용하기에는 해상도와 세부 품질이 부족한 부분이 있었습니다. 이 단계에서는 **Adobe Firefly를 이용해 표지 이미지를 업스케일하고 출력에 적합하도록 개선**했습니다.

이 경험을 통해 이미지 제작도 단순히 생성 단계에서 끝나는 것이 아니라, 실제 사용 크기와 출력 목적에 맞춰 후처리하는 공정이 필요하다는 점을 확인했습니다.

## 이미지 제작 흐름

**GPT에서 초기 보드게임 표지·발표 이미지 방향 설정**  
→ **Codex에서 필요한 장면과 구성 제안**  
→ **Grok에서 제안안을 바탕으로 수정·보강 이미지 제작**  
→ **Adobe Firefly로 필요한 이미지 업스케일·품질 보정**  
→ **웹게임에서 WebP/경량 영상으로 압축·연결**

## 🖼 생성형 그림을 많이 넣으려다, 결국 이모지를 적극 활용하기까지

초기에는 카드 설명과 효과를 더 직관적으로 보여주기 위해 **카드마다 생성형 그림을 많이 넣는 방향**을 시도했습니다. 위험 사건이나 행동의 의미를 이미지로 전달하면 카드가 더 풍부해 보일 것이라 생각했고, 여러 장면과 아이콘 후보를 만드는 데 상당한 시간을 들였습니다.

하지만 실제 제작이 진행되면서 문제가 보였습니다.

- 카드마다 이미지를 새로 만들면 제작 시간이 크게 늘어남
- 비슷한 의미의 카드도 그림 스타일이 조금씩 달라 일관성이 흔들림
- 작은 카드 안에서는 이미지가 오히려 글자를 읽는 공간을 줄임
- 이미지 파일이 늘수록 웹버전의 용량과 자산 관리가 복잡해짐
- 인쇄물에서는 작은 그림의 세부 표현이 생각보다 잘 보이지 않음

결국 모든 정보를 생성형 이미지로 설명하기보다, **기존 이모지와 간단한 기호를 최대한 활용하는 방향**으로 바꾸었습니다. 식량, 돈, 물자, 위험, 연구, 통신처럼 반복해서 등장하는 개념은 이모지와 짧은 기호로 통일하고, 생성형 이미지는 표지·컷씬·캐릭터처럼 실제로 분위기와 서사가 필요한 곳에 집중했습니다.

이 변화는 단순한 타협이라기보다, 무엇을 이미지로 만들고 무엇을 기호로 남길지 구분하는 디자인 원칙으로 발전했습니다. 결과적으로 카드와 UI의 정보 밀도는 낮아지고, 인쇄와 모바일 화면에서도 더 빠르게 읽을 수 있게 되었습니다.

## ✂ 화면에서는 몰랐던 문제 — 실제로 인쇄하고 잘라보기

보드게임 컴포넌트는 화면에서 보기 좋게 만드는 것만으로 끝나지 않았습니다. 초기에는 카드와 공용보드의 비율을 디지털 화면을 기준으로 설계했지만, 실제 A4 용지에 출력해 직접 잘라보고 손에 쥐어 보면서 예상하지 못한 문제가 드러났습니다.

- 카드 크기가 손으로 잡고 섞기에 적절한지
- 카드마다 텍스트량 차이 때문에 물리적 크기나 인상이 달라지지 않는지
- 공용보드에서 각 영역이 실제 플레이 시 충분히 읽히는지
- 재단 후 여러 장을 섞었을 때 울퉁불퉁하지 않은지
- 실제 테이블 위에서 컴포넌트 비율이 과도하게 크거나 작지 않은지

이후 **실제로 인쇄 → 재단 → 플레이 → 불편 확인 → 컴포넌트 비율과 문구 수정 → 재인쇄**의 과정을 반복했습니다. 특히 위험도 카드처럼 셔플이 필요한 컴포넌트는 카드 크기가 일정해야 했기 때문에, 설명을 줄이고 표현을 통일하면서 물리 규격을 맞추는 방향으로 수정했습니다.

AI는 문구 압축, 배치안 정리, 규격 비교에 도움을 주었지만, 최종 판단은 실제 출력물을 손으로 사용해 본 결과를 기준으로 했습니다.

## 📱 실제 모바일 기기로 매번 옮겨가며 수정한 UI

웹게임의 모바일 UI도 데스크톱 브라우저의 개발자 도구만으로 결정하지 않았습니다. 수정된 웹파일을 **실제 사용 중인 모바일 기기로 반복해서 이식해 직접 실행하고 눌러보는 방식**으로 검증했습니다.

PC 화면에서는 괜찮아 보였지만 실제 휴대폰에서는 다음과 같은 문제가 반복해서 발견되었습니다.

- 행동카드를 3열로 배치했을 때 카드가 지나치게 좁아지는 문제
- 하단 진행 기록이 화면 높이를 밀어 올려 주요 정보가 위로 밀리는 문제
- 모바일 가로 화면에서 남은 위험도 카드 현황을 확인하기 어려운 문제
- 버튼과 상세 설명의 위치가 실제 손가락 조작에서 불편한 문제
- 화면 모드에 따라 같은 정보라도 접근성이 달라지는 문제

문제를 발견하면 AI에게 화면 구조와 증상을 설명해 수정안을 만들고, 다시 파일을 모바일 기기로 옮겨 검증했습니다. 그래서 모바일 UI는 한 번에 설계된 결과물이 아니라 **실제 기기 테스트 → 불편 발견 → 수정 → 재이식 → 재검증**이 누적된 결과입니다.

## 🔧 AI 결과를 그대로 믿지 않고 수동으로 점검한 이유

AI를 반복해서 사용하면서 또 하나 중요해진 것은 **버전과 기존 기능을 사람이 직접 확인하는 과정**이었습니다.

프로젝트의 웹게임은 짧은 기간에 많은 버전이 생겼고, 여러 수정사항이 동시에 들어가면서 AI가 현재 작업 중인 파일의 버전이나 과거 규칙을 잘못 인식하는 경우가 있었습니다. 이전 버전의 규칙을 최신 규칙처럼 참조하거나, 이미 수정된 기능을 다시 되돌리는 방향으로 제안하는 위험도 있었습니다.

그래서 후반 작업에서는 다음 원칙을 더 강하게 적용했습니다.

- 수정 전에 현재 파일명과 버전을 먼저 확인
- 기존 기능이 무엇인지 구조를 먼저 파악한 뒤 변경
- 여러 기능을 한 번에 건드리기보다 단계별로 적용
- 업데이트 후 이전 기능이 사라지거나 되돌아가지 않았는지 직접 실행해서 확인
- 버전 로그와 실제 파일 내용을 비교해 기록 오류가 없는지 수동 점검
- AI가 기억하고 있는 과거 설정보다 현재 실행 파일과 실제 플레이 결과를 우선

이 과정은 단순한 오류 수정이 아니라, **AI와 협업할 때도 버전 관리와 검증 책임은 제작자에게 있다는 경험**으로 남았습니다.

## 🧩 이미지 연결과 자산 관리에서 생긴 시행착오

캐릭터 표정과 컷씬 이미지가 늘어나면서 이미지 파일의 이름, 표정 종류, 캐릭터 연결 관계가 복잡해졌습니다. 한 번은 이미지를 수정하는 과정에서 얼굴 이미지 연결이 엉키는 문제가 발생했고, 이후에는 기존 이미지를 함부로 교체하기보다 구조와 연결 방식을 먼저 확인하는 절차를 두었습니다.

이후 포트레잇 이미지를 캐릭터별·표정별로 정리하고 WebP로 압축했으며, 컷씬 이미지도 가능한 한 기존 자산을 재사용하는 방향으로 바꾸었습니다. 이미지가 많아질수록 화려함보다 **분류 가능성, 용량, 연결 안정성**이 중요해졌기 때문입니다.

## 반복 제작 방식

이 프로젝트에서 실제로 반복된 흐름은 다음과 같습니다.

**아이디어 또는 문제 발견**  
→ **AI와 원인·수정 방향 논의**  
→ **규칙·코드·이미지·문서 초안 제작**  
→ **실제 인쇄물 / 실제 모바일 기기 / 실제 웹게임에서 테스트**  
→ **예상하지 못한 문제 발견**  
→ **수동으로 버전·규칙·기능 확인**  
→ **다시 AI와 수정**  
→ **재검증**

이 과정을 반복하면서 AI는 결과물을 대신 만드는 도구라기보다, 제작자가 더 빠르게 가설을 만들고 시험할 수 있게 하는 도구로 사용되었습니다.

## AI를 사용하면서 유지한 제작 원칙

- 최종 규칙과 밸런스 판단은 실제 플레이 결과를 기준으로 결정
- AI가 제안한 내용을 그대로 적용하지 않고 게임 규칙과 충돌 여부를 재검토
- 실제 인쇄·재단·모바일 기기 테스트처럼 물리적·실사용 검증을 반드시 거침
- 모든 정보를 이미지화하지 않고, 반복 정보는 이모지와 기호를 적극 활용
- 이미지 생성·편집은 제3자의 권리를 침해하지 않는 독창적 방식만 사용
- 이미지 용량과 분류 문제 때문에 후반에는 새 이미지를 무분별하게 추가하지 않고 기존 자산을 재사용
- 웹게임은 오프라인 보드게임의 규칙 검증 도구라는 역할을 유지하면서 스토리 기능을 확장
- 버전 번호와 기존 기능은 AI의 기억보다 현재 파일과 로그를 기준으로 수동 확인

## 보고서에서 강조할 수 있는 점

이 프로젝트에서 AI는 단일 도구가 전체 결과물을 대신한 것이 아니라, **기획·구조화·코드·이미지·문서화·후처리 단계에 서로 다른 방식으로 사용된 제작 보조 도구**입니다.

특히 실제 오프라인 플레이에서 나온 피드백, 실제 인쇄 후 발견한 컴포넌트 비율 문제, 실제 모바일 기기에서 발견한 UI 문제처럼 **AI가 직접 경험할 수 없는 영역을 사람이 검증하고 다시 AI에게 돌려주는 과정**이 프로젝트의 핵심 제작 방식이었습니다.

초기에는 생성형 이미지를 많이 넣으려 했지만 실제 카드·모바일·웹 환경을 거치며 이모지와 기호 중심으로 단순화한 과정 역시 같은 맥락입니다. 결과적으로 AI 활용은 자동 제작보다 **사람이 테스트하고 판단하며 AI와 반복적으로 수정하는 제작 공정**에 가까워졌습니다.
